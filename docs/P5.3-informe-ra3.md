# P5.3 - Informe RA3 sobre el despliegue (WildFly contenedor + Gradle)

- Nombre: Ezequiel Ortega

En este informe voy a documentar todo el proceso que segui para desplegar una API REST hecha con Jakarta EE en un servidor WildFly dentro de un contenedor Docker, usando Gradle para compilar el proyecto. La aplicacion es basicamente un CRUD de tareas que guarda los datos en un fichero JSON.

## a) Componentes y funcionamiento de los servicios del servidor

**Explica qué componentes/servicios intervienen en tu despliegue de P5.2 y qué papel tiene cada uno (como mínimo: contenedor Docker, WildFly, aplicación WAR,puertos 8080/9990 y endpoint REST). Ten en cuenta el punto c) sobre el servidor web frontal.**

En mi despliegue de la P5.2 intervienen los siguientes componentes:

- **Docker**: es la plataforma de contenedores que uso para ejecutar WildFly de forma aislada. Me permite facilmente y con buenas practicas levantar y destruir el entorno sin afectar a mi sistema operativo ademas de ser escalable.

- **WildFly**: es el servidor de aplicaciones Jakarta EE (que antes se llamaba JBoss AS). Se encarga basicamente de recibir las peticiones HTTP y enrutar cada una a la aplicacion correspondiente. Internamente usa un motor web llamado Undertow que escucha en el puerto 8080.

- **Aplicacion WAR (crud-file.war)**: es el artefacto que genera Gradle. Contiene las clases Java compiladas, las paginas web (index.html) y la configuracion (web.xml). WildFly lo despliega automaticamente cuando lo copio a la carpeta `deployments`.

- **Puerto 8080**: es por donde se accede a las aplicaciones desplegadas en WildFly.

- **Puerto 9990**: es la consola de administracion de WildFly. Permite gestionar el servidor de forma visual.

- **Endpoint REST** (`/crud-file/api/tasks`): es la URL que expone la API para hacer operaciones CRUD sobre las tareas.

### Flujo de una peticion

1. El cliente (navegador, curl o cualquier cliente http) hace una peticion HTTP a `http://localhost:8080/crud-file/api/tasks`
2. Luego el docker redirige el trafico del puerto 8080 del host al puerto 8080 del contenedor
3. WildFly (Undertow) recibe la peticion y mira el contexto `/crud-file` para saber que aplicacion debe atenderla.
4. Dentro de la app, JAX-RS mira la ruta `/api/tasks` y la envia a la clase `TaskResource.java`
5. El metodo correspondiente (GET, POST, PUT, DELETE) se ejecuta, accede al almacen de datos (FileTaskStore) y devuelve la respuesta en JSON
6. La respuesta viaja de vuelta al cliente

## b) Archivos principales de configuracion y bibliotecas compartidas

### Archivos de configuracion de WildFly

El archivo de configuracion principal de WildFly en modo standalone es:

```
/opt/jboss/wildfly/standalone/configuration/standalone.xml
```

Este archivo controla todo el comportamiento del servidor: datasources (bases de datos), seguridad, logging, subsistema web (Undertow), puertos, interfaces de red, etc.

Para mi despliegue, los ajustes mas relevantes que se podrian tocar ahi son:

- **Puertos e interfaces**: cambiar en que IP y puerto escucha WildFly
- **Logging**: configurar el nivel de log (INFO, DEBUG, etc.) y donde se guardan los logs
- **Datasources**: si en vez de fichero JSON quisiera usar una base de datos real
- **Undertow (servidor web)**: configurar el contexto por defecto, compresion, etc.

Para ver los archivos de configuracion dentro del contenedor ejecute:

```bash
docker exec -it wildfly ls /opt/jboss/wildfly/standalone/configuration/
```

### Dependencias "provided" (compileOnly)

En mi `build.gradle` tengo:

```gradle
dependencies {
    compileOnly 'jakarta.platform:jakarta.jakartaee-api:10.0.0'
}
```

El `compileOnly` (equivalente a "provided" en Maven) significa que esta dependencia solo se usa para compilar, pero NO se incluye dentro del WAR. La razon es que WildFly ya trae todas las librerias de Jakarta EE 10 incluidas. Si las metiera en el WAR tendria conflictos de versiones y el archivo seria mucho mas grande sin necesidad.

La ventaja principal es que el WAR es mas ligero (solo contiene mi codigo) y el servidor se encarga de proporcionar las APIs de Jakarta en tiempo de ejecucion.

## c) Cooperacion con el servidor web (proxy / reverse proxy) y HTTPS

### Situacion en P5.2

En la P5.2 accedi directamente a WildFly por `localhost:8080`, sin ningun intermediario. Esto esta bien para desarrollo pero en produccion no es adecuado porque:

- WildFly queda expuesto directamente
- No hay cifrado HTTPS
- El puerto 9990 (consola de admin) esta accesible

### Configuracion de reverse proxy con Nginx

Para un entorno mas realista, puse un Nginx delante de WildFly como reverse proxy. La configuracion que use es:

```nginx
server {
    listen 80;
    server_name localhost;
    # Redirigir todo HTTP a HTTPS
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name localhost;

    ssl_certificate     /etc/nginx/certs/selfsigned.crt;
    ssl_certificate_key /etc/nginx/certs/selfsigned.key;

    # Proxy a la API
    location /api/ {
        proxy_pass http://wildfly:8080/crud-file/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Proxy a la interfaz web
    location / {
        proxy_pass http://wildfly:8080/crud-file/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

### Que cambia respecto a mi despliegue de P5.2

- **Puertos publicados**: ahora solo publico los puertos 80 y 443 de Nginx. El puerto 8080 de WildFly solo es accesible internamente en la red de Docker, y el 9990 ni se publica.
- **URL de acceso**: ahora se accede por `https://localhost/api/tasks` en vez de `http://localhost:8080/crud-file/api/tasks`. La ruta es mas limpia.
- **Cifrado**: todo el trafico entre el cliente y Nginx va cifrado con TLS.

### Configuracion TLS

Genere un certificado autofirmado con OpenSSL:

```bash
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout nginx/certs/selfsigned.key \
  -out nginx/certs/selfsigned.crt \
  -subj "/C=ES/ST=Cadiz/L=Cadiz/O=IES Rafael Alberti/CN=localhost"
```

Las ventajas de usar HTTPS son:
- **Cifrado**: los datos viajan cifrados, nadie puede ver las peticiones en texto plano
- **Integridad**: se detecta si alguien modifica los datos en transito
- **Autenticacion**: el certificado verifica que el servidor es quien dice ser (en produccion usaria un certificado real de Let's Encrypt)

En mi aplicacion Java no cambio nada. El cifrado TLS lo gestiona Nginx. WildFly sigue recibiendo HTTP normal internamente, que es lo habitual en este tipo de arquitecturas (TLS termination en el proxy).

## d) Mecanismos de seguridad del servidor de aplicaciones

### Medidas aplicadas en P5.2

1. **Credenciales de la consola de administracion**: cree un usuario con contrasena segura (mayusculas, minusculas, numeros y simbolos) mediante `add-user.sh`. Sin estas credenciales nadie puede acceder a la consola de gestion del puerto 9990.

### Medidas que annadiria para produccion

2. **No exponer el puerto 9990**: en mi docker-compose solo publico los puertos 80 y 443 (Nginx). El puerto 9990 de WildFly no se expone al exterior, asi la consola de admin solo es accesible desde dentro de la red de Docker. Si un administrador necesita acceder, puede hacerlo via `docker exec` o mediante un tunel SSH.

3. **Gestion de secretos**: las contrasenas nunca deben estar en el codigo ni en el Dockerfile. En produccion usaria Docker Secrets o variables de entorno inyectadas de forma segura al arrancar el contenedor. El `.gitignore` debe excluir cualquier archivo con credenciales.

4. **Logs centralizados y persistentes**: si el contenedor se borra, los logs desaparecen. Por eso en mi docker-compose use volumenes para persistir los logs de WildFly (`wildfly-logs`). En produccion ademas enviaria los logs a un sistema centralizado (ELK, Grafana Loki, etc.) para poder investigar incidentes de seguridad.

5. **Principio de minimos privilegios**: el contenedor de WildFly no deberia ejecutarse como root. WildFly ya usa el usuario `jboss` por defecto. Ademas, se deberian limitar los recursos del contenedor (CPU y memoria) para evitar que un ataque de denegacion de servicio consuma todos los recursos del host.

## e) Componentes web del servidor de aplicaciones

### Que es el WAR y que contiene

El WAR (Web Application Archive) es un archivo comprimido (como un ZIP) que contiene todo lo necesario para desplegar una aplicacion web en un servidor Jakarta EE. Mi `crud-file.war` contiene:

- `WEB-INF/classes/` - las clases Java compiladas (TaskResource, Task, FileTaskStore, etc.)
- `WEB-INF/web.xml` - configuracion del despliegue web
- `index.html` - la interfaz web de la aplicacion

No incluye las librerias de Jakarta EE porque son `compileOnly` (las proporciona WildFly).

### Contexto / ruta base

El contexto de la aplicacion es `/crud-file`. Se corresponde con el nombre del archivo WAR (`crud-file.war`) sin la extension. WildFly usa este nombre como ruta base automaticamente. Si quisiera cambiarlo podria crear un archivo `WEB-INF/jboss-web.xml` con un `<context-root>` personalizado.

### Contenedor web (Undertow)

Dentro de WildFly, el subsistema **Undertow** es el que se encarga de servir las peticiones web. Es el equivalente a un Tomcat pero integrado en WildFly. Undertow:

- Escucha en el puerto 8080
- Recibe la peticion HTTP
- Mira el contexto de la URL para saber que aplicacion debe atenderla
- Pasa la peticion al framework JAX-RS que la enruta al metodo Java correspondiente

### Desglose de una URL real


http://localhost:8080/crud-file/api/tasks/1
- http => proto
- localhost => host
- 8080 => puerto donde escucha wildfly
- /crud-file => contexto aplicacion (nombre del WAR)
- /api => ruta base de la api
- /tasks => recurso rest
- /1 => id (el id de la tarea)

## f) Parametros necesarios para el despliegue

Estos son los parametros clave que use en mi despliegue:

### 1. Imagen Docker
```
quay.io/wildfly/wildfly:latest
```
Si usara una imagen incorrecta o una version que no soporta Jakarta EE 10, la aplicacion no arrancaria.

### 2. Mapeo de puertos (`-p`)
```
-p 8080:8080 -p 9990:9990
```
Si no mapeo el 8080, no podre acceder a la aplicacion desde mi maquina. Si pongo un puerto que ya esta en uso (ej: `-p 80:8080` pero el 80 esta ocupado), Docker dara error.

### 3. Parametro de arranque de WildFly
```
-b 0.0.0.0 -bmanagement 0.0.0.0
```
El `-b 0.0.0.0` hace que WildFly escuche en todas las interfaces (no solo localhost). Sin esto, desde fuera del contenedor no se puede acceder. El `-bmanagement 0.0.0.0` hace lo mismo para la consola de admin.

### 4. Nombre del WAR
```
crud-file.war
```
Definido en `build.gradle` con `archiveFileName = 'crud-file.war'`. Este nombre determina el contexto de la aplicacion (`/crud-file`). Si lo cambio, la URL de acceso cambia tambien.

### 5. Ruta de despliegue
```
/opt/jboss/wildfly/standalone/deployments/
```
Es la carpeta donde WildFly busca automaticamente los WAR para desplegarlos. Si copio el WAR a otra ruta, no se despliega.

### 6. Version de Java (Gradle)
```gradle
sourceCompatibility = JavaVersion.VERSION_17
targetCompatibility = JavaVersion.VERSION_17
```
WildFly espera bytecode de Java 17. Si compilo con una version superior incompatible, WildFly podria rechazar el despliegue.

### 7. Nombre del contenedor
```
--name wildfly
```
Lo uso como referencia en los comandos `docker cp`, `docker logs`, etc. Si no le pongo nombre, Docker le asigna uno aleatorio y tengo que buscarlo cada vez.

## h) Documentacion de administracion y recomendaciones

### Mini-guia de administracion

Esta guia sirve para que cualquier persona del equipo pueda levantar, desplegar y verificar la aplicacion.

#### Arquitectura del despliegue

1. Cliente (navegador/curl)
2. => Puerto 80/443
3. => Nginx (reverse proxy + TLS)
4. => Red interna Docker
5. => WildFly (puerto 8080 interno)
6. => crud-file.war (API REST)
7. => tasks.json (persistencia en fichero)

#### 1. Levantar el entorno

```bash
# Desde la raiz del proyecto
docker compose up -d
```

Verificar que los contenedores estan corriendo:
```bash
docker compose ps
```

#### 2. Compilar y desplegar una nueva version del WAR

```bash
# Compilar
./gradlew clean build

# Copiar al contenedor de WildFly
docker cp build/libs/crud-file.war $(docker compose ps -q wildfly):/opt/jboss/wildfly/standalone/deployments/
```

#### 3. Comprobar el estado

Ver los logs:
```bash
docker compose logs -f wildfly
```

Verificar que la API responde:
```bash
curl -sk https://localhost/api/tasks
```

Verificar desde el navegador:
```
https://localhost/
```

#### 4. Recomendaciones para evitar errores comunes

- **El WAR no se despliega**: asegurate de copiarlo a `/opt/jboss/wildfly/standalone/deployments/` exactamente. Comprueba los logs para ver si hay errores de compilacion o dependencias.
- **Puerto 8080 ocupado**: si otro servicio usa el 8080, para ese servicio o cambia el mapeo de puertos en docker-compose.
- **Error de permisos con Docker**: tu usuario debe estar en el grupo `docker` (`sudo usermod -aG docker $USER`) o usar `sudo`.
- **Gradle no compila**: asegurate de tener Java 17 instalado (`java --version`).
- **Los datos se pierden al reiniciar**: usa volumenes en docker-compose para persistir los datos (ya esta configurado con `wildfly-data`).
- **Certificado HTTPS no valido**: en desarrollo es normal porque es autofirmado. En produccion usaria Let's Encrypt.

## i) Virtualizacion, nube o contenedores en el despliegue

### Docker Compose

Para esta parte cree un `docker-compose.yml` que une todo: Nginx como servidor web frontal y WildFly como servidor de aplicaciones, conectados por una red interna de Docker.

```yaml
services:
  wildfly:
    image: quay.io/wildfly/wildfly:latest
    user: root
    command: /opt/jboss/wildfly/bin/standalone.sh -b 0.0.0.0 -bmanagement 0.0.0.0
    volumes:
      - wildfly-data:/opt/jboss/wildfly/standalone/data
      - wildfly-logs:/opt/jboss/wildfly/standalone/log
    networks:
      - app-network
    healthcheck:
      test: ["CMD-SHELL", "bash -c 'echo > /dev/tcp/localhost/8080'"]
      interval: 10s
      timeout: 5s
      retries: 12
      start_period: 90s
    restart: unless-stopped
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: "1.0"

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
      - ./nginx/certs:/etc/nginx/certs:ro
    depends_on:
      wildfly:
        condition: service_healthy
    networks:
      - app-network
    restart: unless-stopped
    deploy:
      resources:
        limits:
          memory: 128M
          cpus: "0.5"

volumes:
  wildfly-data:
  wildfly-logs:

networks:
  app-network:
    driver: bridge
```

### Explicacion de las decisiones

- **Volumenes**: uso `wildfly-data` para persistir los datos de la aplicacion (el fichero tasks.json) y `wildfly-logs` para que los logs no se pierdan si se destruye el contenedor.

- **Healthcheck**: WildFly puede tardar en arrancar. El healthcheck verifica que el servidor responda antes de que Nginx empiece a enviarle trafico (`depends_on: condition: service_healthy`).

- **Reinicio automatico**: `restart: unless-stopped` hace que los contenedores se reinicien automaticamente si se caen o si se reinicia la maquina.

- **Limites de recursos**: limito WildFly a 512MB de RAM y 1 CPU, y Nginx a 128MB y 0.5 CPU. Esto evita que un contenedor consuma todos los recursos del host.

- **Redes**: ambos contenedores estan en `app-network`. Nginx puede acceder a WildFly por su nombre de servicio (`wildfly`), pero WildFly no esta expuesto al host directamente (no tiene `ports:`).

- **Solo Nginx expone puertos**: el unico contenedor con puertos publicados es Nginx (80 y 443). WildFly solo es accesible dentro de la red de Docker.
